# Исправление логики выбора атомов и учёта интересов пользователя

## Проблема

Были обнаружены следующие проблемы:

1. **Одинаковое количество атомов для разных планов**: 
   - Daily план (medium) и Full план (long) возвращали одинаковое количество атомов (3)
   - Причина: `text_generation.py` **переопределял** количество атомов, игнорируя значение из `daily_digest_service.py`

2. **Слабый учёт интересов пользователя**:
   - `persona_tags` (интересы) имели вес 0.3, а `trigger` — 1.0
   - SQL-запросы **не фильтровали** атомы по `persona_tags`
   - Атомы с идеальным match по интересам проигрывали атомам с только trigger match

3. **Отсутствие логирования**:
   - Невозможно было отследить, сколько атомов выбирается на каждом этапе

## Внесённые изменения

### 1. `content_atoms_rag.py` — усиление учёта интересов

#### Изменение 1.1: Увеличен вес `persona_tags` в скоринге
```python
# Было:
score += 0.3 * len(atom_personas & query_personas)

# Стало:
score += 0.7 * len(atom_personas & query_personas)

# Плюс добавлен бонус за полное покрытие интересов:
if query_personas and atom_personas >= query_personas:
    score += 0.5  # бонус за полное покрытие всех интересов пользователя
```

#### Изменение 1.2: Приоритизация в SQL-запросах
- Приоритет 1: trigger + persona_tags (идеальный match)
- Приоритет 2: только trigger
- Приоритет 3: только persona_tags
- Приоритет 4: все атомы локали (fallback)

#### Изменение 1.3: Подробное логирование RAG-слоя

### 2. `text_generation.py` — убрана жёсткая логика

#### Изменение 2.1: Использование всех переданных атомов
```python
# Было: переопределение max_atoms по length
# Стало: chosen = atoms (используем ВСЕ переданные атомы)
```

#### Изменение 2.2: Подробное логирование рендеринга

### 3. `daily_digest_service.py` — добавлено логирование

## Итоговая архитектура

```
daily_digest_service.py → определяет max_atoms
  ↓
content_atoms_rag.py → подбирает атомы с учётом интересов
  ↓
text_generation.py → рендерит ВСЕ переданные атомы
```
